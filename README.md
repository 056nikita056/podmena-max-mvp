# Подмена

MVP для управляющего кофейней: одна заявка на срочную смену, поиск по собственному штату, резерву и двум **модельным** внешним источникам, переписка, предложение и отдельное подтверждение кандидата. Рабочая роль в MVP одна: управляющий. Реальные внешние биржи, оформление работника и подтверждение фактической явки не подключены.

## Запуск одной командой

Нужны Docker Engine и Compose. Скопируйте `.env.example` в `.env`. Для локальной проверки без MAX установите `ENABLE_BROWSER_DEMO=1` и задайте длинный случайный `SESSION_SECRET`. Затем:

```bash
docker compose up --build -d
```

Откройте `http://localhost:3000` и нажмите «Войти в локальное демо». Сервер и UI доступны на порту 3000. SQLite находится в Docker volume `podmena_data`. Остановка: `docker compose down`. Повторный запуск той же командой сохраняет данные. Полный сброс volume выполняйте только осознанно: `docker compose down -v`.

Для запуска без Docker: Node.js 24+, `npm ci`, `npm run build`, затем `ENABLE_BROWSER_DEMO=1 SESSION_SECRET=<случайная_строка> npm start`. Сборка нужна, поскольку сервер раздаёт каталог `dist`.

## Проверка за 3–5 минут

1. Войдите в локальное демо. Подготовлен бизнес «Кофейни “Смена”», две точки Москвы и десять синтетических кандидатов. Часовой пояс смен: `Europe/Moscow`.
2. «Найти подмену» → заполните условия → «Создать заявку» → «Запустить поиск». На вкладке «Источники» виден результат каждого обращения; на «Откликах» только подходящие люди.
3. Откройте отклик, напишите сообщение. Сервер сохранит его и добавит помеченный модельный ответ.
4. «Предложить смену»: статус станет «Ожидаем подтверждения». На вкладке «Выход» нажмите «Демо: кандидат подтвердил». Только после этого появится «Подмена согласована».
5. Обновите страницу: заявка, сообщения и назначение остаются. Добавьте согласованного кандидата в резерв и отметьте выход. Невыход можно проверить отдельно: он переводит заявку в статус без подмены.

В разделе «Демо» можно выбрать для **следующей** заявки: успех, отсутствие откликов, отказ, ошибку Профи.ру. Кнопка сброса затрагивает только текущее демо-пространство. Для проверки разделения данных API допускает вторую синтетическую персону `reviewer`, которую UI намеренно не показывает.

## Архитектура и данные

- `web`: React 19, Vite, официальный MAX UI 0.5 и MAX Bridge. Один origin с API.
- `server/http.js`: HTTP-маршруты, сессии, webhook и выдача статических файлов.
- `server/domain.js`: правила состояний и детерминированный модельный поиск.
- `server/store.js`: SQLite через libSQL локально и Turso на Vercel, подготовленные данные и транзакции.
- `tests`: автоматические проверки API, доступа, повторов, подписи MAX и перезапуска.

Время хранится в UTC, отображается в `Europe/Moscow`. Деньги хранятся в копейках. Переходы контролируются сервером; частичный уникальный индекс не допускает два активных предложения на заявку. Смена с известным пересечением исключается из поиска. Сообщения выводятся React как текст без HTML-инъекций. Демо-пространства разделены по подтверждённому MAX user id; локальный тест использует только два фиксированных синтетических профиля.

## MAX и внешние условия

MAX требует существующий бот, `MAX_BOT_TOKEN`, постоянный публичный HTTPS-адрес и привязку URL мини-приложения в настройках бота на платформе для партнёров. Токен остаётся только на сервере. UI передаёт `window.WebApp.initData`; сервер проверяет HMAC-SHA256 по официальному алгоритму и возраст данных до одного часа, затем выдаёт ограниченную сессию. `initDataUnsafe` не используется для входа.

Вызовы MAX API используют включённый в репозиторий **публичный** корневой сертификат удостоверяющего центра. Его не нужно устанавливать в систему пользователя или отключать проверку HTTPS. Бот-токен в репозиторий не включён.

Для повторной проверки подключения выполните `npm run max:check`; подписка уже направлена на `https://podmena-max-mvp-1.vercel.app/api/max/webhook`. Скрипт `npm run max:subscribe` сначала читает существующие подписки и ничего не меняет, если активен другой URL. Webhook требует `X-Max-Bot-Api-Secret`, обрабатывает повторы и отвечает пользователю на `bot_started`. После модельного подтверждения код отправляет уведомление в MAX пользователю, который запустил бота. URL мини-приложения привязывается отдельно в настройках бота; одного API-токена для этого недостаточно. Long Polling одновременно с webhook не запускается.

**Не размещайте `.env`, токен, пользовательскую SQLite-базу или приватный служебный слайд в Git.** Для публичного размещения задайте `ENABLE_BROWSER_DEMO=0`, `APP_PUBLIC_URL=https://...`, `SESSION_SECRET`, `MAX_WEBHOOK_SECRET` и `MAX_BOT_TOKEN`. `DEMO_MODE=1` оставляет модельные источники и сценарии; это не отключает авторизацию.

Чтобы заменить модельную площадку реальной, понадобятся согласованный публичный API партнёра, право на публикацию и обмен сообщениями, авторизация, формат вакансий/откликов, лимиты, обработка отказов и договорённость об использовании персональных данных. Текущий код не отправляет реальные объявления наружу.

## API и ограничения

Контракт описан в [`openapi.yaml`](openapi.yaml). Для проверки основных вызовов подготовлен [`DATA-API.yaml`](DATA-API.yaml) с локальной версией формата. Схема автоматической проверки организаторов нам не выдана, поэтому совместимость с её валидатором не заявлена. Тестовые данные: [`docs/demo-data.json`](docs/demo-data.json).

В рабочем окружении Vercel заданы `TURSO_DATABASE_URL`, `TURSO_AUTH_TOKEN`, `SESSION_SECRET`, `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET` и `APP_PUBLIC_URL`; значения секретов хранятся только в настройках окружения. Для проверочного доступа в обычном браузере в отдельном окружении можно задать `ENABLE_BROWSER_DEMO=1`; такой вход работает только с синтетическими данными. `api/index.js` передаёт запросы `/api/*` существующему серверу, а `vercel.json` собирает Vite и размещает функции. Локальный URL или временный туннель не являются адресом сдачи. Подписка MAX подтверждена через API; реальная доставка сообщений и запуск в мобильном MAX ещё не проверены. UX на 375 px и широком экране проверен в браузере; проверка внутри мобильного клиента MAX отдельно необходима.
